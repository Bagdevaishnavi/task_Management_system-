# TaskFlow --- Task Management System

> A clean, responsive task-management frontend built with **HTML5, CSS3,
> Vanilla JavaScript, Bootstrap 5, and REST APIs**.

## 1. Project Overview

**TaskFlow** is a browser-based task management application that allows
authenticated users to manage their daily tasks from a simple dashboard.

The application provides:

-   User registration and login
-   JWT-based authenticated API requests
-   Task creation
-   Task listing and task details
-   Task editing
-   Task deletion with confirmation
-   Task status management
-   Task priority management
-   Dashboard task statistics
-   Status and priority charts
-   User profile viewing
-   User profile editing
-   Profile image upload validation
-   Logout/session clearing
-   Dedicated 404 and 500 error pages
-   Responsive Bootstrap-based UI
-   SweetAlert2 notifications

The frontend communicates with a remote REST API and stores the returned
access token in browser `localStorage`.

## 3. Main Features

### 3.1 Authentication

Users can create an account and sign in through the authentication
pages.

#### Signup

The signup flow:

1.  Collects form values.
2.  Sends a `POST` request to the authentication API.
3.  Receives an access token after successful registration.
4.  Stores the token in `localStorage`.
5.  Redirects the user to the dashboard.

Endpoint:

``` text
POST /api/auth/signup
```

#### Login

The login flow:

1.  Collects email/password form data.
2.  Sends credentials to the backend.
3.  Receives an access token.
4.  Stores the token under `accessToken`.
5.  Redirects to the dashboard.

Endpoint:

``` text
POST /api/auth/login
```

### 3.2 Session Management

The application checks:

``` javascript
localStorage.getItem("accessToken")
```

Protected API requests send:

``` http
Authorization: Bearer <accessToken>
```

Logout removes the stored token:

``` javascript
localStorage.removeItem("accessToken");
```

## 4. Task Management

### Add Task

Users can create a new task through the Add Task page.

Endpoint:

``` text
POST /api/tasks
```

The request contains the task form data and the authentication token.

Typical task fields include:

-   Title
-   Description
-   Priority
-   Status

### View Tasks

The task details page retrieves the authenticated user's task list.

Endpoint:

``` text
GET /api/tasks
```

The returned task data is dynamically rendered into Bootstrap-based
cards.

Each task card displays:

-   Task title
-   Status
-   Priority
-   Description
-   Edit action
-   Delete action

### Edit Task

The edit page reads the task ID from the URL:

``` text
edit-task.html?id=<task-id>
```

The application fetches the user's tasks, finds the requested task by
`id` or `_id`, and fills the form with the current values.

Task details are updated through:

``` text
PATCH /api/tasks/{id}
```

The current implementation updates:

-   Description
-   Priority

The task title is intentionally treated as immutable by the frontend.

### Status Update

Status is updated through a dedicated endpoint:

``` text
PATCH /api/tasks/{id}/status
```

Example status values used by the UI:

``` text
pending
in-progress
completed
```

The frontend also normalizes status values so variations such as
`in_progress`, `in-progress`, `complete`, and `done` can be displayed
consistently.

### Delete Task

Before deletion, TaskFlow shows a SweetAlert2 confirmation dialog.

After confirmation:

``` text
DELETE /api/tasks/{id}
```

The task list is then refreshed.

## 5. Dashboard

The dashboard calculates task statistics from the authenticated task
list.

It displays:

-   Total Tasks
-   Completed Tasks
-   Pending Tasks
-   In Progress Tasks

### Status Chart

A doughnut chart represents task distribution by status.

### Priority Chart

A bar chart represents task distribution by:

-   High
-   Medium
-   Low

The dashboard does not require a separate statistics endpoint. Instead,
it derives the statistics from:

``` text
GET /api/tasks
```

This keeps the frontend logic simple and allows the dashboard to reflect
the current task data.


The UI can display information such as:

-   Full name
-   Gender
-   Personal mobile number
-   Address

-   Guardian phone number

Profile updates use:


## 19. Environment / Configuration

The API URL is currently written directly in the JavaScript files:

``` javascript
https://intern-crud-task-api.onrender.com
```

For a larger production application, it would be better to centralize
the API base URL into one configuration file, for example:

``` javascript
const API_BASE_URL =
    "https://intern-crud-task-api.onrender.com";
```

Then construct endpoints from that value.

This reduces duplication and makes development/staging/production
configuration easier.

## 20. Security Considerations

The frontend uses an access token for authenticated API requests.

Current approach:

``` javascript
localStorage.setItem("accessToken", result.accessToken);
```

Important production considerations:

-   Do not expose secrets in frontend JavaScript.
-   Validate all data on the backend.
-   Enforce authorization on every protected backend route.
-   Use HTTPS in production.
-   Validate uploaded files on the server as well as the client.
-   Consider an HttpOnly, Secure cookie-based authentication strategy
    where appropriate.
-   Do not treat frontend validation as a security boundary.
-   Avoid logging sensitive authentication data in production.
-   Implement appropriate token expiration and refresh behavior on the
    backend.

## 22. Current Limitations / Improvement Opportunities

The project is functional as a frontend task-management application, but
the following areas can be improved for a production-grade
implementation.

### API Configuration

The API base URL is duplicated in multiple files.

**Improvement:** create a single API configuration module.

### Form Submission

Some forms use button click handlers rather than relying entirely on the
form `submit` event.

**Improvement:** use:

``` javascript
form.addEventListener("submit", ...)
```

This improves keyboard accessibility and standard form behavior.

### Client-Side Validation

The current frontend performs some validation, especially for profile
images.

**Improvement:** add reusable validation for required task/auth/profile
fields.

### Authentication UX

The current application checks whether a token exists.

**Improvement:** also handle:

-   expired tokens
-   unauthorized `401` responses
-   token refresh
-   automatic session expiration

### Rendering Safety

Task content is inserted using HTML template strings.

**Improvement:** carefully escape user-controlled text or use DOM
APIs/textContent to reduce XSS risk.

### State Management

The application currently keeps form data in local JavaScript objects.

**Improvement:** introduce a small reusable state/service layer if the
application becomes larger.

### Accessibility

Further improvements could include:

-   stronger keyboard navigation
-   improved focus states
-   ARIA feedback for dynamic updates
-   better form error messaging
